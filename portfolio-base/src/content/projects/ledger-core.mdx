## Context

A ledger is the part of a business that cannot be wrong. Every other feature can be redesigned; the record of what moved,
when and why has to stay correct through every change around it. Describe here who uses the system, what the books cover
and which constraints shaped it.

<Sidenote label="Language">
  Write the domain terms down before the first folder exists: account, entry, posting, period. The structure of the code
  follows that vocabulary, not the framework's.
</Sidenote>

The first decision is where the boundaries go. Postings, balances and closing periods each have their own rules and their
own pace of change, so each one becomes a bounded context with its own model instead of one shared schema.

## Architecture

The core exposes ports: interfaces that say what it needs (store an entry, publish a posting) without saying how.
Adapters implement them for a database, a message bus or an HTTP API. The core is compiled and tested without any of
them.

<Sidenote label="Rule of thumb">
  If a test of the core needs a container, a port is missing.
</Sidenote>

## Testing strategy

Most of the confidence comes from fast tests of the core against in-memory adapters. A thinner layer of contract tests
checks that every real adapter honours the same port, so swapping storage is a configuration change, not a rewrite.
